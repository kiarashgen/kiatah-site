# Computational pages: source and production brief

2 October 2026. Working editorial proposal for the site, based on the retained files in `C:/Users/kiarash/Desktop/compute` and the current V9.7 site. This is a production map, not a claim that all four pages are already built. Originals stay in `compute`; selected public derivatives will get their own project folders and source records.

## The intended site structure

Four substantial project pages, reached from one quiet Computational Work index:

1. **Structures through computation** — bridge, tower and shell in one authored investigation. The bridge is the human and built anchor; tower and shell broaden the geometry and structural inquiry. Grasshopper/Karamba can be identified in methods, never as the page title. These are three related studies, not one historical model or one shared analysis run.
2. **Learning to play** — Hokm and X/O as distinct experiments in agents, state, actions and evaluation. A visitor should be able to play, inspect an actual saved decision, and see what the retained checkpoint did versus later rule-based improvements.
3. **Reading a regulation** — the Persian Mabhas 19 retrieval and fine-tuning experiment, with LangChain/RAG lineage. Show a real question, retrieved passage, response or abstention, corpus construction and its limitations. It is an experiment, not a regulation authority.
4. **The queryable building** — Dynamo/Revit information extraction, IFC relationships, voxel representation and pathfinding. Make their lineage visible but do not claim the independent historical files formed one completed product. The sample IFC is a software fixture, not an authored building design.

The index should make the four inquiries legible by **what is computed**: forces and form; decisions; evidence and language; building relationships and routes. Software names belong in small method labels. Use the site's black/cream atmosphere and project-specific blue for analytical states. Existing text-heavy report plates are reference material, not final page images. Rebuild important diagrams with source geometry and site-native text, preserving responsive layout and accessibility.

Evidence classes to show beside each relevant visual:

- **Retained source:** original screenshot, recording, definition, model or checkpoint.
- **Source-derived reconstruction:** exact saved graph, topology, model export or source-linked inspector; no fresh native application run implied.
- **New computation:** reproducible calculation on retained inputs, with its assumptions and environment shown.
- **User-confirmed history:** bridge group construction and test, pending physical media and measured results.
- **Open lead:** promising source whose pairing, ownership or runtime behavior has not been checked.

The current `#graph` site case compresses most of this work into one IFC image and an embedded 69-page review. It also carries an unrelated “Harakat Festival / May 2025” label. That case should be replaced during the computational page build; the review can remain a private source index.

## Depth requirement for every page

The pages need more than a hero and a diagram. Each should contain **distinct kinds of evidence**, each doing a different job: an original artifact or recorded interface; a clean source-derived visual; a precise method or data view; a working interaction; a result/failure or comparison; a small original-source/download panel; and a direct personal account of what was learned or built. Do not satisfy this by repeating one plate style ten times. A good page should let a visitor see the object, operate the method, inspect a result and trace the result back to a retained file.

| Page | Image/object range | Interaction range | New assets to make from material already present |
| --- | --- | --- | --- |
| Structures | Original bridge alternatives, clean bridge model, actual force and displacement states, native tower states, shell form/mesh/field, GH ancestry | Five-state comparison, real axial member picker, controlled result layers, tower orbit/profile, shell form/mesh/field toggle, graph lineage explorer | Signed force viewer begun; build matched original screenshot ledger, clean site-native force legend, source-linked GH mini-graphs, 3D synchronized variants, sectional cutaways |
| Games | Card table, original code/checkpoints, replay hand/trick states, paired result chart, X/O board, action-score trace | Hokm step/scrub/inspect, legal-move reveal, X/O play under three separately named policies, chosen-board explanation | Recompose saved replay as cards/table, generate compact SVG card/state assets, accessible game controls, condition-labeled comparison |
| Regulation | Original PDF/page, video stills, RTL question/passage/answer, corpus structure, run screenshots, error/abstention | Recorded episode scrub, source highlight, context-overlap compare, curated question browser | Extract exact timecoded episodes and source pages, rebuild clean RTL flow and overlap visualization, distinguish generated answer from reviewed answer |
| Building | Safe Dynamo graph/model/output chain, IFC object geometry, source-ID relation, voxel layers, plan and 3D route, door states | Entity query/highlight, graph-to-model trace, voxel slice, route endpoint choice, close/open door, radius/pitch comparison | Safe model-output trace, source-linked semantic+3D inspector, validated route animation, clear 2D/3D section and door cutaway |

This range is a production target, not an invitation to invent evidence. When an original output is absent, make a new computation with explicit inputs, reproduce it, and identify it as new. When a physical record is absent, keep its place and claim boundary clear until the real record is retrieved.

## Page 2 — Learning to play

**Opening:** a real decision, not a generic neural-network diagram. The visitor sees a Hokm hand, trick, legal actions and selected card, then can step through the retained 40-decision self-play deal. A second, smaller X/O playable experiment becomes the contrast: a finite game where exact values can be checked exhaustively.

**Flow:** rules/state → original trainer and checkpoints → saved action in context → replay and paired evaluation → what the state representation misses → X/O playable board → raw checkpoint decision → immediate win/block and exact-value layers → what the improvement actually came from.

**Strong assets already in hand:** four original Hokm scripts, two checkpoints, original Tic-Tac-Toe code and two checkpoints, new portable inference and evaluations. The Hokm trainer uses one 166→256→256→52 Q network for seats 0/2 against random seats 1/3; the saved play loop uses one checkpoint in all four seats. The retained simplified engine has random trump and first team to seven tricks. The new evaluation spans 1,920 paired games; best-v-random is 408/640. Its replay logs 40 actions, hands, legal sets and Q scores. The game inspector already works in the browser. X/O has 4,520 reachable nonterminal boards and 18→64→32→9 checkpoints. Later win/block and exact-value rules raise decision quality; the checkpoints were not retrained. Large scores are not probabilities.

**Make for the site:**

1. A bespoke Hokm table, compact on mobile, with step/jump, legal-card emphasis, team score and actual action-score inspection. Source and evaluation engine label stays visible.
2. A two-state visual comparing original training seats and all-four-seat replay, because those are different setups.
3. A sample-state/encoding diagram using real cards, showing the missing trick-order distinction without suggesting it caused the saved outcome.
4. A small playable X/O board with mode switch: retained network, network plus win/block, and exact-value filter. Display chosen move and its actual score/value; explain the added rule.
5. One compact results panel with test conditions and reproducible seed, plus a link to the full record. Avoid a manufactured historical learning curve.

**Retrieval:** seek original training logs, screenshots or notebooks and dated checkpoint provenance if available. Without them, present the checkpoints and later evaluations as they are; never infer training progress from their filenames.

## Page 3 — Reading a regulation

**Opening:** a Persian question and one real retrieved passage, in an excellent RTL reading layout. The saved 90-second RAG recording can sit in a small archival video panel; it documents an actual interface and an unanswered/abstaining episode. The regulation itself should be quoted minimally and source-linked, with legal text handled as source material rather than portfolio copy.

**Flow:** source document → chunk/retrieval → displayed context → response or abstention → generated question/answer corpus → saved fine-tuning setup and three run screenshots → why neither loss nor generated “golden” labels establish correctness → precise lesson and next bounded experiment.

**Strong assets already in hand:** Persian PDF/DOCX, retrieval code, original interface recording, dataset of 912 unique questions but only 206 distinct contexts, three training screenshots, Qwen3-8B 4-bit rank-16 LoRA config, corpus-overlap audit, source-linked review queue. Of 205 adjacent contexts, 203 share at least 80 exact characters; a question-level split could leak common passages across partitions. No complete adapter weights were recovered; no independent answer accuracy is established. The earlier experiment was described by the user as mostly unsuccessful/finished.

**Make for the site:**

1. A curated three-example question viewer: a supported retrieval, an abstention/failure, and an ambiguous or overlap-sensitive example, chosen only after inspecting the exact source and video frames. Each shows source page/chunk, what the interface displayed and a careful observation.
2. A text-free retrieval pipeline diagram, with explanatory HTML outside the artwork; no fake similarity numbers.
3. A context-overlap interaction: choose two source contexts and reveal the exact shared text, plus why this weakens a simple split. Use actual dataset records and page citations.
4. A small training-record panel with the three original screenshots and exact observed loss/steps. Label them observations, not an evaluation curve.
5. A closing “what I would test next” section as a proposed bounded, human-reviewed source-citation evaluation, clearly future work.

**Retrieval:** original adapter weights if they still exist in an older archive, exact PDF page references, prompt/config environment, and any independent human evaluation. If none is recovered, the page remains a candid experiment with a strong source-grounded interface and corpus audit. Do not present regulation answers as advice.

## Page 4 — The queryable building

**Opening:** a question about a building element or route, with the source model and answer shown together. This page should feel spatial, not like a generic colored graph.

**Flow:** Dynamo/Revit extraction → identified model elements and output schedule → IFC hierarchy and entity IDs → one wall/opening/door relationship trace → geometric voxelization → route between named rooms → close a real door and see disconnection → discuss the representation and its limits. The page must label the transition from historical separate experiments to the later source-derived integrated demonstration.

**Strong assets already in hand:** 16 Dynamo graphs, two inventoried RVT files, one original XLSX, IFC source samples, older `vox_pfin.py`, modular prototype, Neo4j/LLM query scripts, semantic inspector, native IFC GLB, deterministic same-floor voxel route and sensitivity data. The fully attributed co-named Dynamo graph has 14 nodes/15 connections, but no fresh Revit execution. `natural light.dyn` is a room/opening/orientation information graph, **not** daylight simulation. The source IFC semantic inspector shows 59 selected entities/76 relations from 10,824 STEP entities; wall #243 → opening #10710 → door #8411 is source-linked. The later route uses AC20-FZK-Haus, a reference fixture: 136×117×71 grid at 0.10 m, modeled support/headroom/body radius, 15/15 same-floor pairs and a selected 10.776955 m path. Closing door #17468 or #19504 disconnects that pair. Cross-level is unsupported. The retained older 52×82×40 voxel array lacks coordinate metadata and is not the same model/grid. The separate browser Routing Lab is a **synthetic 2D fixture**.

**Make for the site:**

1. A Dynamo graph-to-model trace with one chosen authored input, saved node chain, selected element IDs and actual returned table, after opening a **copy** of the RVT/graph in the right application. Do not run auto-mode or deletion graphs against originals.
2. A source-linked IFC question panel: choose storey/space/element, show source ID, relation and synchronized 3D highlight. Avoid inferring adjacency from a hosting relationship.
3. A voxel cutaway with geometry/solid/floor/clearance/room masks and pitch explanation. Use the validated deterministic dataset, not the metadata-unknown NPZ.
4. A route viewer from real room IDs: route, unreachable door-closed state, body-radius and pitch sensitivity. Show the model fixture name and assumptions at all times. The interaction is computation exploration, not an egress approval.
5. A lineage strip distinguishing historic code, later recovery/new computation, and proposed future natural-language interface. The modular LLM tool is a placeholder; do not show it as a working assistant. Any query generator needs a read-only boundary and element citations.

**Retrieval:** original Revit model/graph pairing, saved element IDs and output evidence; source for the selected IFC fixture and rights for site redistribution; any user's own building model suitable for a future authored-model demonstration. `work3`/`work4` carry another person's name and stay out. `work5.dyn` has a deletion operation. The reference building should never quietly become “Kiarash's design.”

## Build order and acceptance

**First, preserve the evidence.** Create one source manifest per project with original absolute path, relative public derivative, hash, creator/credit, date if known, evidence class and claim boundary. Copy only selected public derivatives; avoid moving, renaming or cleaning originals. Keep private credentials, license files and raw personal records out of site packages.

**Second, make one complete page at a time.** Structures first because the bridge has the most concrete human story and the source bank already has geometry/analysis. Games next because its replay and playable board can be tested precisely. Regulation follows after exact episode/source review. Building follows after model/graph matching; the validated IFC fixture can still support its own explicitly labeled section before a Revit rerun.

For every page, build its own `content/projects/<slug>/`, `public/assets/projects/<slug>/`, page module and scoped styling. Author text and page drawing remain editable through the site's local authoring system. Avoid the shared navigation and pavilion work while those are active in this checkout. Update the Computational Work index and remove the old catch-all embed only when the first complete page and link structure are ready.

**A page is reviewable when** its opening image identifies the subject, its main interaction operates on real retained/new data, every numerical claim points to conditions and source, source downloads work, image order and credits are correct, and desktop/narrow-screen views have been visually checked. A successful build alone is insufficient. Keep PDF production and publication for later.
